## Context

`/api/me` is built from `ICurrentUser` without a database read, and the live relay calls it often (to re-validate the
session), so it must stay cheap. `users` lives on the primary. `UserProvisioningPreProcessor` creates the row
on first sight. `_authenticated.beforeLoad` calls `getMe()` on every navigation and puts `me` in the router context.
The `<html>` element is rendered by `__root.tsx`'s shell, which runs before `_authenticated`.

## Goals / Non-Goals

**Goals:** account-level preferences, no theme flash, a cheap read.

**Non-Goals:** preferences for anonymous users (every page is signed-in), piece-set choice beyond Cburnett, sound.

## Decisions

1. **A jsonb column on `users`, not a table.** One row per user already exists, and preferences are one small object.
   `Preferences` is nullable: null means defaults, which keeps the migration free of backfill. _Alternative:_ a
   `user_preferences` table. Rejected: a join or second query for no benefit.
2. **A separate endpoint, not a field on `/api/me`.** `/api/me` stays database-free for the relay.
   `GET /api/me/preferences` reads through FusionCache (`prefs:{userId}`, `Cache:PreferencesMinutes` on the existing
   `CacheOptions`, default 60). PUT writes the primary and evicts the entry, and Redis makes that eviction
   reach every node.
3. **Validation in one place.** `PreferencesValidator` (FastEndpoints `Validator<>`) checks every field against the
   allowed sets, and the allowed sets live in `Authentication/Preferences.cs` next to the
   defaults (with the user provisioning, so no one-file `Users/` folder). `SettingsTests`-style drift
   test: the frontend's `lib/preferences.ts` lists the same values (checked by a vitest that reads a shared JSON
   fixture generated by the backend test).
4. **The BFF loads both in `beforeLoad`** (`Promise.all([getMe(), getPreferences()])`) and puts `prefs` in the
   router context. The attributes go on the Shell's root element (`data-board`, `data-theme`, `data-coords`), not
   on `<html>`: the shell renders before `_authenticated`, and every signed-in page is inside the Shell, so the
   CSS variables cascade from there. `color-scheme` follows `data-theme` in CSS.
5. **Optimistic settings page.** Each control calls `putPreferences` with the whole object through `useCommand`,
   updates the router context on success (`router.invalidate()` is not needed: a local override state is enough
   until the next navigation re-reads), and puts the control back on failure.

## Risks / Trade-offs

- [An extra request per navigation] → It is cached, tiny, and runs in parallel with `getMe()`.
- [Two lists of allowed values (C# and TS)] → The drift test above fails the build if they differ.

## Migration Plan

The migration adds a nullable column (no downtime). Roll back by redeploying the previous images. The column can
stay.
